# 確認を人間とエージェントに振り分ける基準

動作確認のうち、**どこまでをエージェントが firefox-devtools MCP で行い、どこから先を人間に依頼するか**を判断するための文書。

エージェント側で完結する確認の手順は [development.md](development.md) の「4. 動作確認する」にある。**人間に依頼する分の手順書は常設していない。** 依頼が必要になった時点で、そのとき確認したいことに合わせて都度書くこと（書き方は後述）。

ブラウザ操作の制約の一次情報は `AGENTS.md` の「ブラウザ操作」節。

## 判定の根拠となる 3 つの制約

| # | 制約 | 出典 |
|---|------|------|
| A | `moz-extension://` への `navigate_page` / `new_page` は BiDi が拒否するため、ポップアップ UI を開いて操作できない | `AGENTS.md` |
| B | ページのコンソールを読むツールが存在しない。`restart_firefox` + `devtools.console.stdout.content` で stdout 経由に迂回できるが、再起動でプロファイルが作り直される | `AGENTS.md` |
| C | 実インスタンスの資格情報（ID・パスワード・2FA）と、それを使った認可の意思決定はエージェントが持てない | 本質的制約 |

## 振り分けの手順

確認したいことを「**どの状態を作り**、**何を観測して**判定するか」に分解し、両方が MCP で閉じるかを見る。

### 1. 状態を作れるか

拡張機能側の状態は、ストレージへの直接書き込みでほぼ任意に作れる（制約 A の回避策）。ページ側の状態も、遷移とクリックで作れる範囲なら問題ない。

作れないのは、**実インスタンスにログインしていないと変えられない状態**（サーバー側のユーザー設定、認証済みセッション）。これは制約 C にあたり、人間の担当。

### 2. 観測できるか

MCP の観測経路はスクリーンショット・DOM スナップショット・`evaluate_script` の3つ。判定材料がこのいずれかに現れるなら、エージェントで完結する。

現れないのは次の3種類。

- **ポップアップ UI の内側にしかないもの** — 制約 A。UI を開けない以上、そこでの操作結果も表示も観測できない
- **ブラウザ chrome が描画するもの** — ネイティブツールチップなど。ページのスクリーンショットの外側にある
- **コンソールにしかないもの** — 制約 B

### 3. 判定が機械的か

観測できても、**識別しやすいか・混同しないかといった知覚的な判断**は人間のもの。撮影までは自動化できるので、人間に依頼するのは判断だけになる。

### 4. 副作用を伴わないか

実アカウントでの公開操作は、実行してよいかの判断が人間のもの。モックアカウントは通信が発生しないため、この制限を受けない。

## 制約ごとの補足

### A: ポップアップ UI を開けない

`AGENTS.md` の回避策（拡張機能の UUID を取得 → `oauth-callback.html` を `window.open` → その realm で `browser.storage.local.set`）で、**アカウントが登録済みの状態を作る**ことはできる。

ただしこれは状態を作る手段であって、UI の検証ではない。**「ポップアップで操作しないと確認できないこと」と「ポップアップで設定した状態でしか起きないこと」は別物。** 後者はストレージ直書きでエージェントが確認できる。前者（追加フロー、入力バリデーション、選択操作、ポップアップ自身の表示と文言）だけが人間の担当。

### B: コンソールを読めない

stdout 経由に迂回すれば自動化できるが、代償としてプロファイルが作り直され、拡張機能の再インストールと UUID の取り直しが必要になり、OAuth で得たトークンも失われる。

**人間に依頼するか迂回するかは、その時点でプロファイルを捨てられるかで判断する。** 捨てられないなら、コンソールを使う確認を OAuth より先に済ませる順序にする。

### C: 資格情報と副作用

インスタンスのホスト名入力までは自動化できるが、その先のログイン画面と認可画面は人間が操作する。確認用アカウントをモックと Mastodon の2段階に分けているのはこのためで、**通信を伴わない範囲はモックアカウントで人間の手を借りずに進められる。**

サーバー側のユーザー設定（テーマなど）も同じ理由でログイン状態が必要だが、**設定を変えたあとの観測はエージェント側で行える**。人間に依頼する範囲は「切替操作だけ」に絞ること。

## 人間に依頼する手順を書くとき

依頼文はその都度書く。次を満たしていれば足りる。

- **エージェント側でできることを先に済ませてから書く。** development.md の範囲を通しておかないと、人間に依頼した確認が拡張機能以外の理由で落ちたときに切り分けられない。
- **依頼するのは上の基準で人間しかできないと判定した部分だけにする。** 前後の状態作りと観測はエージェントが引き受ける（テーマ切替なら「切り替える」だけを頼み、切替後の撮影と比較はこちらで行う）。
- **順序の制約を先に解消しておく。** コンソール出力を読む確認と OAuth を要する確認の両方があるなら、コンソール側を先に回す（補足 B）。
- **副作用の対象を明示する。** 実インスタンスでのお気に入り・ブースト・ブックマークは他者の投稿への公開操作。どの投稿に対して行うかを決めたうえで依頼すること。
- **何を見て合否とするかを書く。** 知覚的な判断を頼む場合は特に、比較対象（ライトテーマとダークテーマ、ホスト側の状態色など）まで指定する。
